## Objetivo

Levantar una instancia EC2 en AWS que sirva CertiDoc en producción, con
despliegue automático por tag `v*` usando el workflow ya versionado.

## Lo que ya está hecho

- Workflow `.github/workflows/deploy-ec2.yml` — build de imagen backend a
  GHCR, build estático frontend, rsync a EC2, restart de docker compose y
  health check.

## Lo que falta hacer (pasos del humano)

### 1. Provisión de la instancia

- AMI Ubuntu Server 22.04 LTS.
- Tipo `t3.small` (2 vCPU, 2 GB RAM) — suficiente para el MVP.
- EBS gp3 20 GB.
- Security Group con puertos 22 (SSH desde IP propia), 80 y 443 (público).
- Elastic IP asociada y opcionalmente DNS A record apuntando al dominio.

### 2. Bootstrap (ejecutar en la instancia una vez)

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y docker.io docker-compose-plugin nginx certbot \
  python3-certbot-nginx rsync
sudo usermod -aG docker ubuntu
sudo mkdir -p /opt/certidoc /var/www/certidoc
sudo chown ubuntu:ubuntu /opt/certidoc /var/www/certidoc
```

### 3. Archivos en /opt/certidoc/

- `docker-compose.prod.yml` con servicios `db` (postgres:16) y `backend`
  (imagen `ghcr.io/hdballestan/isaia_gupo1-backend:latest`). Backend
  publica en `127.0.0.1:8000`, no expuesto al SG.
- `.env` con variables: `DATABASE_URL`, `JWT_SECRET`, `VT_API_KEY`,
  `FRONTEND_ORIGIN`, `CORS_ALLOWED_ORIGINS`.
- `nginx.conf` en `/etc/nginx/sites-available/certidoc`:
  - `location /` → `root /var/www/certidoc; try_files $uri /index.html;`
  - `location /api/` → `proxy_pass http://127.0.0.1:8000;`
  - Headers estándar de proxy (`X-Forwarded-For`, `X-Real-IP`, `Host`).
- Habilitar TLS: `sudo certbot --nginx -d certidoc.tu-dominio.com`.

### 4. Secrets en GitHub repo

Ir a Settings → Secrets → Actions y crear:

| Secret | Valor |
|---|---|
| `EC2_HOST` | IP o dominio de la instancia |
| `EC2_USER` | `ubuntu` |
| `EC2_SSH_KEY` | Contenido de la llave privada .pem (formato OpenSSH) |
| `VITE_API_URL` | `https://certidoc.tu-dominio.com/api/v1` |
| `DEPLOY_HEALTH_URL` | `https://certidoc.tu-dominio.com/api/v1/certificates` |

Las credenciales de runtime (`DATABASE_URL`, `JWT_SECRET`, `VT_API_KEY`,
`FRONTEND_ORIGIN`) viven en `/opt/certidoc/.env` en la instancia, no en
GitHub Secrets, porque el workflow no las necesita — el backend las lee del
env al arrancar el contenedor.

### 5. Primer deploy

```bash
git tag v1.0.0
git push origin v1.0.0
```

El workflow se dispara automáticamente. Verificar en pestaña Actions.

### 6. Documentar

Crear `docs/deploy/ec2.md` con:

- Diagrama de red (usuario → CloudFlare opcional → nginx → backend / dist).
- Comandos de bootstrap completos (copiar de arriba).
- Estrategia de rollback: `docker compose -f docker-compose.prod.yml pull
  IMAGE@sha256:<hash-anterior> && up -d`.
- Plan de backup de PostgreSQL (cron diario con `pg_dump` a S3 o EBS
  snapshot).
- Comandos de monitoreo básico: `docker compose logs -f backend`, `journalctl
  -u nginx`.

## Criterios de aceptación

- [ ] Tag `v1.0.0` disparado dispara el workflow sin errores.
- [ ] `https://<dominio>/api/v1/certificates` retorna el catálogo.
- [ ] `https://<dominio>/` sirve el frontend.
- [ ] TLS válido (certificado Let's Encrypt activo).
- [ ] `docs/deploy/ec2.md` existe y documenta todo lo anterior.

## Riesgos y mitigación

| Riesgo | Mitigación |
|---|---|
| Perder la llave SSH | Guardar copia cifrada; habilitar Session Manager de SSM |
| EBS se llena | Alarma CloudWatch en 80% de disco |
| Leak de secrets en logs | No imprimir `.env` en logs; usar `set +x` en scripts |
| Cost overrun | Budget alert en AWS ($15/mes límite) |
